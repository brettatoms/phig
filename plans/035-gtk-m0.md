# 035 — GTK Client M0

Retroactive index entry for shipped work. The execution plan and its ledger are
the detailed record; this file exists so the index shows the change.

Depends on plan 034 — M0 reads phig only through `libphig`'s C ABI, per the
interface discipline in the root `CLAUDE.md`.

## What shipped

Three components, in C against the raw GTK4 and libadwaita C APIs (not gtkmm):

- `PhigGalleryModel` — a custom `GListModel` holding a page LRU, not the whole
  collection
- `ThumbLoader` — an async, cancellable queue resolving thumbnail paths and
  loading files into textures
- the GTK shell

The two components holding logic are headless-testable and are tested
(`gtk/tests/test-gallery-model.c`, `gtk/tests/test-thumb-loader.c`, 13 tests
across two binaries); widget rendering is not.

M0 is read-only: browse and open. No scan, organize, remove, tags, or search —
those need plan 031's ABI surface.

## Known miss

**M0 did not meet its 60 fps criterion**: 95% of frames over the 16 ms budget,
worst frame 83 ms. None of the four tuned values (page radius, loader threads,
texture cache bytes, placeholder cap) moved it. Diagnosis from the code:
nothing scales a thumbnail to the cell — a 512 px cached thumb
(`core/thumbs.cpp:13`) uploads into a 200 px cell (`gtk/src/main.c:10`) and the
GPU downscales every frame. `thumb_loader_request` takes `max_dim` and discards
it (`gtk/src/thumb-loader.c:389`).

Outlined in `docs/plans/2026-08-05-thumbnail-sizing-zoom-hidpi-outline.md`,
deliberately parked pending an isolating measurement. **Every M0 performance
number was measured at one 200 px cell size and does not generalise to a
zoomable grid.**

The whole-app design spec also requires crash isolation via a `phig-decode`
worker pool ("a malformed image never crashes the app"). Measurement since
found 0 crashes in 12,684 decode probes, so that requirement is not
demonstrated; the spec has not been updated.
