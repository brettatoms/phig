# 071 — GTK M1: Browse and Annotate

## Goal

M0 is a thumbnail grid over one catalog, opened read-only. M1 makes the client
usable for day-to-day browsing and annotation, and safe by construction: every
operation it can start is one whose rules all hold today. It draws its screens
from plan 047, which stays the design for the full app.

## The safety boundary

The test for what M1 may expose is the rule record, not judgment: an operation
is in only if no rule binding it is `violated` or `partial` in a way that can
lose user data.

**In.**

- **Reads**: paged queries, per-image metadata, tags, gallery, tag and gallery
  counts, thumbnail and full-image decode. Nothing written.
- **`metadata.write`**: tag add and remove, gallery set and clear, favorite.
  Every rule binding it holds: R28 (IMMEDIATE transactions), R78 (a write names
  its images), R79 (gallery assignment replaces unless asked otherwise), R55
  (the writer lock is taken without waiting).
- **`scan.walk` alone**: indexing new and changed files through
  `ScanEngine::run_workers`, never `run_reconcile`, as libphig's index
  operation already does. R80, the violated rule on scan, is about reconcile
  running after a failed walk; with no reconcile it cannot arise. R35 keeps a
  re-indexed row's id and metadata. R58 is `partial` for scan only in reporting:
  a cancelled scan of a directory with no media reports completed. It loses
  nothing.

**Out, each behind the plan that makes it safe.**

| Operation | Open rules | Waits for |
|---|---|---|
| Deleting rows for missing files (scan reconcile) | R80 violated; R04, R25, R59 partial | 041 |
| Organize (copy, move) | R40 violated (041), R08 violated (059) | 041, 059 |
| Remove, empty trash; acting on duplicates | R61, R68 violated | 064's `core/` part |
| Face rebuild | R60 partial | 063's decision |
| Thumbnail cache clean | R77 violated | 053 |

Plan 047's context menus list Delete…; M1 shows no destructive action at all
rather than a disabled one.

## Scope

**Gallery (047 Screen 1).**

- Sidebar: All Photos, Favorites, Galleries and Tags with counts
  (`get_gallery_counts`, `get_tag_counts`). People and Duplicates are not shown.
- Filters as removable chips, ANDed, mapped onto `Database::SearchCriteria`:
  tag (all of), gallery, favorite, date range, camera, make, media type,
  extension.
- Search: filename and path, as a glob through `matches`. 047's free-text search
  across EXIF has no `core/` query behind it and is out of M1.
- Sort: date (default, newest first), date oldest first, filename, size. 047's
  sharpness sort has no `SortKey` and is out.
- Multi-select with a selection bar: tag, gallery, favorite. No delete.
- Empty states: no photos (with Scan…), no matches (with clear filters), and a
  catalog that cannot be opened (with its error).

**Viewer (047 Screen 2).**

- Full image scaled to fit, previous and next, the thumbnail shown until the
  decode arrives. Decode happens in `collection.cpp` and reaches widget code as
  a `GdkTexture` (gtk/CLAUDE.md).
- Metadata pane: filename, date, camera, exposure, size, blur score, tags as
  removable chips with add, gallery, favorite. No people, no GPS (plan 013).
- Open in the system viewer and show in the file manager. M0's activate already
  launches the file.

**Scan… (047 Screen 6, adding only).**

- Pick a directory and recursive and hidden options; runs `run_workers` on a
  worker thread with progress and cancel in a non-modal bar (047 Screen 8), the
  gallery browsable meanwhile.
- The dialog says what it does: it adds new and changed files and never removes
  rows for files that are gone.
- No `--force`, no faces, no thumbnails pass; thumbnails are generated on
  demand as today.

## Shape of the work

**The seam.** Each capability is a new `collection.h` function with a fake, per
gtk/CLAUDE.md: filtered and sorted `count`/`page`, one image's metadata and
tags, tag and gallery counts, the three metadata writes, full-image decode, and
an index operation with progress and cancellation. The fake gets each one.

**Catalog access.** The catalog is the user's default (see Decisions). M0 opens
it with `CatalogAccess::Read`. M1 opens with `Write`,
which requires the catalog to exist and migrates it, so the client still never
creates a catalog by opening one (R70). A missing catalog is the empty state,
and Scan… is the one path that creates it (`Create`), matching the CLI, where
only `scan` creates.

**Locking.** The client follows libphig's discipline, which R55 records: a
metadata write takes the writer lock without waiting and, when a CLI command
holds it, the client says the collection is busy and changes nothing. The index
operation takes no lock, as libphig's does.

**A standing rule for the client.** gtk/CLAUDE.md's removal rule widens to every
destructive action: anything that deletes, moves or overwrites goes through a
`core/` plan the user reviews and then applies, never a confirmation dialog
around a one-shot call. M1 has none, and the rule is written down before the
first one arrives.

## Testing

- Each new seam function is tested against a real catalog in `test-collection`,
  the way M0's are: filters and sort against seeded rows, metadata writes
  changing exactly the named images, the busy case with the lock held by
  another process, an index adding files and deleting no row for a file that
  went missing.
- Widget behaviour is tested against the fake, per gtk/CLAUDE.md.
- The by-hand checks M0 established stay: a full-range scroll with 0 GTK
  warnings, and closing the window while an operation runs exits cleanly. Scan
  adds one: cancel mid-index leaves the catalog consistent and the window
  responsive.

## Decisions

Decided 2026-11-13.

- **One catalog: the user's default.** The client opens the catalog phig
  resolves by default (`phig::gtk::default_catalog`, as M0 does) and offers no
  way to open another. An Open Catalog… action is not in M1.
- **Tag and gallery names stay free text.** Nothing restricts them. Since R87
  they cannot steer an organize, and nothing else reads them as paths.

## Prerequisite for the scan

Re-indexing an edited photo deletes its face labels today (R36,
`core/database.cpp`); plan 072 keeps them. M1's Scan… ships after 072, and is
built last so the rest of M1 does not wait on it.
