# 054 Phase 3, workstream A — test-gap triage

Which of the rules' `test_gap` records can be closed by writing a test, which
are waiting on something else, and which are permanent. This is the input to
the work of closing them; it writes no tests.

Measured at `234b85c`: **80 rules, 54 carry a `test_gap`.** Of those, **46
anchor only in `core/` or `libphig/`** and **8 have an anchor under `cli/`**
(R68, R69, R70, R73, R77, R78, R80, R81 — five `cli/`-only, three mixed).
The 46 are triaged below.

**The 8 `cli/`-anchored ones are deliberately excluded.** Every one is
`status = "violated"`, and the violation is that the guard sits in the wrong
layer. Plan 053 (R68, R77, R78), 043 (R70), 060 (R69, R73, R81) and 041 (R80)
move that logic into `core/`, which rewrites the anchor, the statement's
enforcement site, and therefore the test. A test written against the code where
it stands today is thrown away by the move.

The three buckets:

- **Closable** — a test can be written today, against the code as it stands,
  that pins the claim. Each entry says what the test has to assert.
- **Blocked** — closing it needs something else first: a code fix the rule is
  waiting on, an entry point that does not exist, a fixture phig has no way to
  build.
- **Unclosable** — no test can pin it and the gap is permanent.

Counts: **30 closable, 14 blocked, 2 unclosable.**

Two rules that a plan will rewrite are still in Closable, because the rewrite
does not touch the claim: R43 and R76 both bind `scan.walk`, which 041 and 043
leave alone.

## Closable

**R07 — two labelers racing for the same candidate.** Two threads running
`identify_person` for different people over one candidate set. Assert that the
two runs' `labeled` counts sum to the candidate count rather than twice it, and
that every labeled face is within threshold of the person it got. Delete
`person_id IS NULL` and the sum doubles. The interleave has to be forced, not
hoped for: hold the write lock from a third connection so the first run's phase
2 blocks while the second run's phase 1 reads the candidates as unlabeled —
the technique `IdentifyTest.NameDoesNotLabelAFaceItDidNotMatchWhenARebuildRecyclesIds`
already uses. Does not touch the `embedding = ?` clause; that is R71.

**R13 — an unreadable path is never deleted by scan.** `chmod 0000` a
subdirectory holding an indexed file, run `ScanEngine::run_reconcile` with
`ignore_mount_warning`, assert the row survives and `result.skipped_check_failed`
is 1. Skip under `geteuid() == 0`, as
`RemoveExecTest.RmOrphansNeverRemovesUnreadablePathsEvenWithIgnoreMountWarning`
does.

**R14 — the flag means the same thing on scan.** Index files under
`dir/sub/`, delete `sub/` entirely, run reconcile twice: without the flag,
assert the rows survive and `skipped_parent_missing` counts them; with it,
assert they are deleted. Every listed test drives `rm`; neither branch of
scan's half is covered.

**R15 — the mount guard with a mixed set.** Two rows deletable (files gone,
parent present) and one `parent_missing`, no flag: `removed_paths.size() !=
db_paths.size()`, so the guard does not fire. Assert the two are deleted and
the third survives, with every tracked file gone from disk. That is the case
the three listed tests step around.

**R17 — the peek only decides whether to open an operation.** Reconcile with
`removed_paths` empty and the only work demotable: a JPEG on disk whose
same-basename RAW is indexed. Assert `demoted == 1` and `removed == 0`. Today
both `run_reconcile` tests have a non-empty `removed_paths`, so the block is
entered whatever the peek answers.

**R18 — the entry and the change roll back together.** Install a
`BEFORE DELETE ON images` trigger raising `ABORT`, then call
`delete_paths_logged` with an `op_id`. Assert it throws, the row is still
there, and `operation_entries` holds no `purge_row` for it — the entry was
inserted before the failing `DELETE` and must be gone. Same family as the
`PRAGMA query_only=ON` injection `OrganizeExecTest` already uses: SQL only, no
seam in production code.

**R20 — dry-run rm.** Two additions to `RemoveExecTest.RmDryRunTouchesNothing`:
`SELECT COUNT(*) FROM operations` is 0 after the run, and — as a second case
against a `db_path` that does not exist — the file is created and
`schema_version` is current. Both clauses were measured by hand; neither is
asserted.

**R21 — the preview is side-effect-free only below `cli/`.** Subprocess:
`phig cp <dest> --dry-run --db <path that does not exist>`, assert exit 0, no
destination tree, and that the database file now exists at the current schema
version. `cmd_organize` is in `cli/main.cpp` and is not linked into
`phig-tests`, so the binary is the only way in;
`RemoveExecTest.CliRefusesNonInteractiveConfirmationEvenWithPipedYes` is the
pattern.

**R23 — a trashed file's row is purged in the same operation.** Drive `cmd_rm`
in `Trash` mode with logging on, then assert the newest operation holds both a
`trash` entry whose `src` is the file and a `purge_row` entry whose `src` is
the same path. The three listed tests all call `execute_trash_action` directly,
which writes no `purge_row`.

**R26 — a path with no row.** Call `delete_paths_logged({present, absent},
op_id)` and assert the return is 1, that the absent path produced no entry, and
that the present row went. Reachable today only through a concurrent writer,
which is why the branch exists; the call itself needs no concurrency.

**R30 — the interrupted state between transfer and delete.** With the R18
trigger blocking `DELETE FROM images`, run reconcile over the relink/demote
overlap the two listed tests build. Assert the state the statement names: tags
on both rows, gallery on the target, faces on the target alone, every stale row
still present. Then drop the trigger, re-run reconcile, and assert the end
state equals an uninterrupted control — the "next scan's cleanup" half the gap
says is untested.

**R31 — the exception path and the committed operation row.** Two tests. With
the R18 trigger, run reconcile (and `cmd_rm`) with logging on: assert each
throws and leaves its operation row `interrupted`. Separately, call
`log_begin_operation` and read the `operations` row from a second `Database`
on the same file without finishing it: assert it is visible and `in_progress`.
That is the whole of "commits its operation row on its own before the first
entry"; killing a process adds nothing a committed-and-unfinished row does not
already show.

**R33 — disk first, log after, no compensation.** `PRAGMA query_only=ON` after
`log_begin_operation`, then `execute_trash_action`. Assert it throws, the
source is gone, the trash directory holds exactly one file, and no `trash`
entry exists. The window is the point: the file is not moved back.

**R36 — an unchanged file keeps the name someone typed.** Add a person label
to the face in `DatabaseTest.ReinsertSameContentKeepsFaces` and assert
`faces.person_id` still names them after the re-insert; assert the label is
gone in the changed-content sibling. The `ScanEngine` half — the `has_faces`
guard against a duplicate second set — needs a real detection run and so gates
on `face_path_blocker()`, like the other ten face tests.

**R38 — every transfer pass finishes before anything is deleted.** Two pieces.
With the R18 trigger blocking the first `DELETE`, assert the relink pass *and*
both demote passes completed — interleaved deletion would leave the later
passes undone. And a Live Photo demotion driven through `run_reconcile` rather
than by calling `demote_live_photo_rows` directly, using the committed
`live_photo_still.jpg` / `live_photo.mov` fixtures, which carry the identifier
the peek looks for.

**R42 — a sidecar is never indexed.** One scan over a directory holding a photo
and its `.xmp`: one row, and it is the photo. The gap names this test itself.

**R43 — a JPEG beside a RAW gets no row.** `ScanEngine` over a directory
holding `IMG_1.CR2` and `IMG_1.JPG`, asserting one row and that it is the CR2.
`tests/data/truncated_ojpeg.cr2` works as the RAW: the JPEG beside it is tier 1
of the RAW pixel source, so the row decodes (`RawDecodeTest.UsesSidecarJpegWhenPresent`
relies on exactly this), and `has_sibling_raw` skips the JPEG before any
decode. The RAW analogue of
`ScanEngineLivePhoto.IndexesTheStillAndNotItsPairedVideo`.

**R44 — a skipped parent carries nothing.** Write a sidecar next to the source
in `OrganizeEngineTest.ApplySkipsItemsWithNoDestination` and in
`ApplySkipsAnItemWhoseDestinationBecameOccupied`, and assert it is still beside
the source afterwards. Two files and two assertions.

**R46 — removal leaves a Live Photo's video alone.** Insert a row for
`live_photo_still.jpg`, put `live_photo.mov` beside it under the same stem,
call `remove_media_with_sidecars`, assert the `.mov` is still on disk and got
no entry. The still-and-video pair is the half of the statement that rests on
reading `find_sidecars`.

**R49 — who takes the lock.** Two assertions are genuinely missing, and both
can be made at the ABI with a `WriterLock` held for the duration: a query on
the same context still succeeds ("no read takes it"), and a direct
`Database::insert` — a writer that takes no lock — succeeds while it is held
("never excludes a writer that takes none"). The third thing the gap implies is
missing is not: `AbiMutate.WriteFailsWhileAnotherProcessHoldsTheWriterLock` and
`WriteSucceedsAfterTheLockIsReleased` already pin that a mutating ABI call is
refused while the lock is held — they are cited by R55, not by R49. What
remains beyond the ABI is the CLI, which needs one subprocess pair: `phig tag
add` refuses while the lock is held, `phig search` does not.

**R52 — the witness must show the window was entered.** Add to
`FacesEngineRun.ImageDeletedMidRunIsSkippedRatherThanAbortingTheRun`:
`r.errors > 0`, and at least one progress message containing "image no longer
in the database". `FacesEngine::run` counts that skip and publishes that text,
so a run whose timing misses the race now fails instead of passing
identically.

**R53 — the busy timeout precedes the first statement.** Create a database that
is not yet in WAL mode, hold an `EXCLUSIVE` transaction on it from another
connection for a few hundred ms, and construct a `Database` on it from another
thread. Assert construction succeeds and took at least that long. Set the
timeout after `PRAGMA journal_mode=WAL` and the construction throws
`SQLITE_BUSY` instead. The lock is held by the test, so the window is forced
rather than raced — which is what the listed test cannot say.

**R54 — `SQLITE_OPEN_FULLMUTEX` earns its keep.** Measured on this machine
(Apple system SQLite 3.51.0): `sqlite3_shutdown()`,
`sqlite3_config(SQLITE_CONFIG_MULTITHREAD)`, `sqlite3_initialize()` all return
`SQLITE_OK` after SQLite has already been used, and in that mode a connection
opened without the flag has a null `sqlite3_db_mutex` while one opened with it
does not. So: switch the library to multi-thread mode, construct a `Database`,
assert `sqlite3_db_mutex(db.db_ptr()) != nullptr`, restore `SERIALIZED`. That
test fails with the flag removed, which is precisely what the two listed tests
cannot do. Two cautions: it mutates process-global SQLite state, so it must run
with no other connection open, and the measurement above is this machine, not a
CI runner.

**R64 — a symbol bump moves MINOR.** Parse `libphig/include/phig/phig.h` for
its exported `phig_*` declarations and assert the count equals the entry
recorded for the current `PHIG_ABI_VERSION_MINOR` in a committed table. Adding
a symbol then fails until either MINOR moves and the table gains a row, or
somebody deliberately falsifies the row for the current minor. `check_abi_version`
already covers the header-against-CMake half; this is the half it says it
cannot reach.

**R65 — `phig_op_progress` gains no field.** A `sizeof` pin in
`tests/test_libphig_c_compile.c`, in the same negative-width-bitfield form as
the enum pins already there. The gap names the test. Writing it moves the rule
from `unenforced` to `holds`.

**R72 — the other three entry points.** A test per entry point that establishes
it can detect before it writes: `FacesEngine::run` over a non-empty selection,
and — as subprocess cases — `phig face name` and `phig search --face`. Each
asserts the refusal names what is missing and that nothing was written, and
each gates on `face_path_blocker()` being non-empty, exactly as the two
existing witnesses gate the other way. **One clause of this gap does not
close:** no test on one build can establish that 4.8.0 is the right floor, and
that sentence must stay in the record rather than be dropped when the rest is
written.

**R74 — selection at the operation, not just the predicate.** For each bound
operation family, one run with an `--exclude` that asserts the excluded file
and its row survived: `cmd_rm`, `OrganizeEngine::apply`, `ThumbsEngine::run`,
`FacesEngine::run`, and a metadata write. Plus one subprocess case for the
`tag`/`gallery`/`fav` route, whose selection goes through
`cli/main.cpp:select_paths` and has no test at all. The largest item here; the
five listed tests all call `passes_selection` directly.

**R75 — flags do not decide deletions.** Index a `.jpg` and a `.mov`, rescan
with `--media video`, assert the `.jpg` row is still there. Then the two halves
the gap says are uncovered entirely: index a file under a subdirectory and
rescan non-recursively; index a hidden file with `--hidden` and rescan without
it. Both times the row survives because the file is on disk.

**R76 — no `--force` value re-detects faces.** Insert a row with a labeled
face, then scan with `force.hash` and `force.faces` both set: assert the file
was reprocessed and the face and its label survived. A second assertion for the
dead field: with only `force.faces` set, `result.processed` is 0 — the file is
skipped on mtime, because nothing reads that flag.

**R79 — the parser branch behind `--no-overwrite`.** Two subprocess
assertions: `phig gallery set <name> --no-overwrite` leaves an existing
assignment alone, and `phig gallery clear --no-overwrite` exits 1 with
`Unknown option`. The three listed tests pass the flag to `Database` as a bool
and never reach the parser.

## Blocked

Eleven of these are blocked for one reason: the rule's `status` is `violated`
or `partial`, the code does not satisfy the statement, and the only honest test
fails. Writing it now would be writing a failing test to chase a fix somebody
else owns, which Phase 3 says not to do. The owning plan is named in each case;
none is closed.

**R04 — `partial`, plan 041.** The snapshot has no tag field because no code
path writes one, and there is no restorer to round-trip against (020 deferred
`phig undo`; 053 records that the log has no reader in `core/`). Round-tripping
is what "sufficient to rebuild" means, so nothing short of 041 plus a reader
closes it.

**R08 — `violated`, plan 059.** No code path implements overwrite-replaces.
The listed test pins the contrary behaviour on purpose.

**R25 — `partial`, plan 041.** `delete_paths` — the unlogged branch — writes no
snapshot at all. A test asserting the statement fails today; a test asserting
what happens today is a regression test for a behaviour 041 inverts.

**R27 — `violated`, plan 060.** `OrganizeEngine::apply` writes `completed`
whenever it was not cancelled, errors or not, while `cmd_rm` writes
`interrupted` on any per-file failure. rm's half could be pinned now, but the
gap is the disagreement, and closing it means fixing organize.

**R40 — `violated`, plan 041.** No code path writes the snapshot the statement
requires. 041's Testing section already specifies the two tests; they belong to
that plan, not this one.

**R48 — `violated`, plan 060.** An item whose carry throws is counted as both
applied and failed. A test asserting "once" fails today.

**R50 — `violated`, plan 039 plus a `cli/` follow-up.** `lock_path()` ignores
`--db`, so a run against a non-default database locks the wrong file. 039
closes the `core/` half; the call site in `cli/main.cpp` needs its own change
before any CLI command locks the right file.

**R56 — no fixture phig can build.** The remaining gap is entirely
`cli/main.cpp`'s handler swap. The half that matters — a signal arriving
*while* `run_reconcile` runs, which is what the swap exists for — cannot be
forced: reconcile publishes nothing, so a subprocess has no synchronization
point to aim at, and a mistimed signal passes for the wrong reason. The other
half (Ctrl-C during the worker phase, then reconcile still runs) is forceable
off the first progress line and is worth writing, but it does not cover the
swap. Worth noting separately: this gap asks for coverage of code outside the
rule's own `enforced_at`, which is `core/scan_engine.cpp`; by the record's own
layering the handler swap is either its own `cli/`-anchored rule or a plan
item.

**R58 — `partial`, plan 056.** `ScanEngine::run_workers` and
`OrganizeEngine::apply` have no cancellation check on an empty selection, so an
already-cancelled run over nothing reports `completed = true`. That is the
uncovered branch, and a test of it fails until 056 adds the guard.

**R59 — `partial`, plan 041.** The reconcile half is a claim about an absence —
there is no reconcile plan to override. The only assertion available today is
that `run_reconcile` takes no plan argument, which is a tripwire on the exact
signature 041 is going to change.

**R60 — `violated`, plan 060.** `face rebuild` destroys person labels with no
authorization. A test asserting authorization fails today.

**R61 — `violated`, plan 053.** A dry-run `rm` returns nothing to inspect; the
preview exists only on stdout. Nothing to assert until `cmd_rm` returns a
value.

**R62 — `partial`, plan 053.** The unwrapped entry points are the defect, so an
enumeration check over them fails today. Reaching the hole otherwise needs an
allocation failure inside an unwrapped call, which needs an allocator seam phig
does not have.

**R66 — `partial`, plan 053.** Faces has no plan phase, which is why the rule
is partial. The negative half — that no entry point takes a callback — is an
absence over the whole ABI surface and belongs in a check, not a test.

## Unclosable

**R34 — durability across a power loss.** The statement is about what survives
when the machine stops between a commit and a WAL checkpoint. A test process
cannot stop the machine, and simulating it (truncating the WAL by hand) tests
the simulation rather than SQLite. The statement is read from the pragma and
SQLite's documented behaviour, and it stays that way. This is why the rule is
`unenforced` rather than `holds` with a gap.

**R71 — no path rewrites an embedding in place.** The statement is that the
`embedding = ?` clause refuses nothing the other two clauses have not already
refused, *because* nothing in phig ever changes a face row's embedding. That is
an absence over the whole codebase, including code not yet written: a test can
only exercise paths that exist, and the one witness already forges the state
with a raw `UPDATE` because no phig path produces it. The nearest thing that
would help is a source check for an `UPDATE faces SET embedding`, which is a
lint rule and not a test.

## Proposed order

Grouped so each step reuses the fixture the one before it built. Effort is
relative, not measured.

1. **Assertions inside tests that already exist.** R44, R36 (label clause),
   R52, R42, R20, R26, R46. No new fixtures; each is a few lines in a file the
   suite already has. Do these first — seven gaps for the cost of one.
2. **Scan reconcile scenarios**, in `tests/test_scan_engine.cpp` on the
   existing `ScratchCollection` and `insert_row` helpers: R15, R14, R13, R17,
   R75, R43, R76, and R38's Live Photo half. Eight new cases, one fixture,
   no new machinery.
3. **The fault-injection helper**: a `BEFORE DELETE ON images` trigger that
   raises `ABORT`, plus the existing `PRAGMA query_only=ON` trick. Build it
   once, then R18, R33, R31, R30 and R38's ordering half. Five gaps, one
   helper. Highest value per test in the list — these are the interruption
   windows nothing currently enters.
4. **R23**, in `RemoveExecTest`: the one gap that needs `cmd_rm` driven end to
   end with logging on.
5. **Concurrency**: R07 (forced window in `test_faces_identify.cpp`), R53 and
   R54 (both in `test_database.cpp`, both mutating process-wide or
   file-wide state — keep them apart from the rest). R54 is the fiddliest test
   in the list; R53 is straightforward.
6. **ABI pins**: R65 (small, and it moves a rule out of `unenforced`), then
   R64 (needs a committed symbol-count table and a decision about whether it
   lives in the test or in `scripts/rules.py`).
7. **Subprocess cases**, all needing `phig_binary_path()`: R21, R79, R49's CLI
   half. Group them so the binary-missing skip is written once.
8. **The two large ones**: R74 (one selection test per bound operation, plus
   the `select_paths` subprocess case) and R72 (three entry points, each gated
   on `face_path_blocker()`). Leave R72's floor clause in its `test_gap`.

Every closed gap edits its rule's `tests` list and its `test_gap` in the same
commit, then re-runs `python3 scripts/rules.py --check --emit` with the
regenerated views committed alongside. A gap that shrinks rather than closes —
R72 is the one here — keeps the sentence that is still true.

## Two findings about rules this triage did not cover

**R29 has no `test_gap` and needs one.** Its only test is
`DatabaseConcurrency.ConcurrentMigrationIsSafe`, the same test R53's gap
describes as statistical: two threads race `init_schema` on a rolled-back
database, and if one finishes before the other starts, the second sees the
current version and does nothing, so the run passes without exercising the
re-check inside the transaction. R53 records that weakness against itself; R29
rests on the identical evidence and records nothing. This is the failure mode
the record exists to catch, so R29 should carry the same gap.

**R22's threshold has no negative case.** The statement makes a broad removal
"at least half the collection and twenty rows or more". Every `cmd_rm` test in
the suite either sets `assume_yes = true` or drives the broad path at 20 of 20,
so nothing shows that a narrow removal proceeds without a confirmer. A
threshold that had drifted to "always broad" would pass every listed test.
Lesser than R29, but the same shape.

**Two imprecisions, reported rather than corrected.** R25's gap says three
`ScanEngine` tests delete files and reach `delete_paths`; a fourth,
`ScanEngine.RunWorkersAloneDeletesNothing`, deletes two files and calls
`run_reconcile` directly, taking the same branch. It does not re-scan, so the
sentence is defensible as written and the count does not change the gap's
point. Left alone rather than edited, since editing a rule means regenerating
the views for a word.

R49's gap says the lock's call sites "are in `cli/main.cpp`, outside this
anchor and outside every test". There are also call sites in
`libphig/mutate.cpp`, and those are under test — R55 cites two of them. The
conclusion the gap draws is still true, because "no read takes it" is asserted
nowhere, but a reader who trusts the premise will write a test that already
exists.
