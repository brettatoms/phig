# Schema v9 — Stable `images.id` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate `images.id` to `INTEGER PRIMARY KEY AUTOINCREMENT` so an image
id names the same image for as long as that image exists, closing R72 and
unblocking plan 053's id-based selection surface.

**Architecture:** A schema v9 migration rebuilds the `images` table, copying
rows with their ids preserved so `sqlite_sequence` is seeded to the current
maximum. Because `image_tags.image_id` and `faces.image_id` are both
`REFERENCES images(id) ON DELETE CASCADE` and `PRAGMA foreign_keys=ON` is set on
every open, the rebuild must run with foreign keys disabled — and the pragma is
a no-op inside a transaction, so the migration loop sets it around each
migration's transaction, with `PRAGMA foreign_key_check` inside that
transaction before the commit.

**The cascade is not a schema defect.** `ON DELETE CASCADE` is what phig wants
when a photo is genuinely removed: `core/database.cpp:951` relies on it in
`delete_paths`, and `insert` uses an upsert rather than `INSERT OR REPLACE`
specifically because REPLACE would delete the row and cascade the tags away.
The anomaly is SQLite's: `DROP TABLE` with foreign keys enabled performs an
implicit `DELETE` of every row first, and that fires the cascade. PostgreSQL
refuses such a drop unless told to cascade, and then drops the constraint
rather than child rows; MySQL/InnoDB refuses as well. Disabling foreign keys
around a table rebuild is SQLite's documented procedure, not compensation for a
bad constraint.

**Why the pragma is unconditional.** Making it conditional on the version
number would put the collection's tags at the mercy of the next migration
author noticing that their table has FK children. The cost of leaving it off
for migrations that do not need it is nil — none of v2 through v8 depends on a
cascade firing mid-migration — and `foreign_key_check` before each commit
covers the case the enforcement would have caught.

**Tech Stack:** C++20, SQLite (system libsqlite3 3.51.0 on macOS), GoogleTest,
CMake.

**Why the pragma is load-bearing.** Measured against the system SQLite, running
the rebuild both ways on a table with two images and two `image_tags` rows:

| `foreign_keys` during rebuild | images after | tag assignments after | `foreign_key_check` |
|---|---|---|---|
| `OFF` | 2 | 2 | 0 violations |
| `ON` | 2 | **0** | 0 violations |

What is lost is precise, and worth stating exactly because "the tags are gone"
overstates it in one direction and understates it in another. The `tags` and
`people` rows survive; no tag or person is ever destroyed. What the cascade
takes is every `image_tags` row — all tag and favorite assignments for every
image — and every `faces` row, which is not an association but the data
itself: embeddings, boxes, and the person labels on them, re-derivable only by
re-running detection, and in the labels' case not re-derivable at all (R60).

With the pragma on, the `DROP TABLE images` did that and the migration reported
no error. That silence is the failure this plan is built to
prevent, and it is why Task 3 Step 3 turns the pragma back on to prove the test
can fail.

**`foreign_key_check` does not catch that failure, and must not be mistaken for
the thing that does.** Run against the database the cascade just emptied, it
reports `0` violations: deleted children leave no orphans, so the database is
perfectly consistent and simply has no tag assignments and no faces. The check
guards the opposite defect — a rebuild that loses parent rows and strands
children. The pragma is what prevents the destruction; Task 3's test is what
would detect it.

Two things that were checked rather than assumed: `ALTER TABLE images_new
RENAME TO images` immediately after `DROP TABLE images` does **not** trip
SQLite's post-rename schema reparse, because the rename restores the name the
child tables reference before the check runs; and copying rows with explicit
ids seeds `sqlite_sequence` to the maximum, so a later insert continues above
it rather than filling the gap — verified by inserting ids 1, 2 and 7, deleting
7, and getting 8.

## Global Constraints

- Migrations are forward-only. `migrations()[N]` upgrades from version N-1 to N.
- `CURRENT_SCHEMA_VERSION` in `core/database.cpp` is the single version
  constant; bump it in the same commit as the migration it names.
- Every migration step runs inside `BEGIN IMMEDIATE TRANSACTION` and re-reads
  the version inside that transaction, so a concurrent first-run does not
  re-apply DDL.
- First-party code builds with `-Wall -Wextra`; CI configures `-DPHIG_WERROR=ON`.
- Format with `clang-format -i` (Google style, 4-space, 100-col) before every
  commit.
- Data-safety changes ship with real-behavior tests, not mocks.
- Changing a guard means updating its rule record in the same commit, then
  running `python3 scripts/rules.py --check --emit` and committing the
  regenerated `rules/by-*.md` views alongside it.
- Commit messages: plain prose, no attribution trailers, no mention of AI
  assistance.

```cpp
int Database::foreign_key_violations() {
    sqlite3_stmt* stmt = nullptr;
    if (sqlite3_prepare_v2(db_, "PRAGMA foreign_key_check", -1, &stmt, nullptr) != SQLITE_OK) {
        throw std::runtime_error("prepare foreign_key_check: " + std::string(sqlite3_errmsg(db_)));
    }
    int count = 0;
    while (sqlite3_step(stmt) == SQLITE_ROW) count++;
    sqlite3_finalize(stmt);
    return count;
}
```

- [ ] **Step 6: Teach the migration loop to toggle the pragma**

In `core/database.cpp`, replace the loop body at lines 495-523. The pragma must
be set before `BEGIN` and restored on every exit path, including the throwing
one:

```cpp
        for (int v = db_version + 1; v <= CURRENT_SCHEMA_VERSION; v++) {
            // Foreign keys off for every migration, not only the ones that
            // rebuild a table. SQLite's DROP TABLE performs an implicit DELETE
            // of every row before dropping, so dropping a table with ON DELETE
            // CASCADE children destroys their rows and still reports success —
            // and the pragma is a no-op inside a transaction, so it cannot be
            // set where a migration runs. Conditioning it on the version number
            // would leave that to the next migration author to notice. The
            // pragma is per-connection, so no other process is affected.
            exec("PRAGMA foreign_keys=OFF");
            exec("BEGIN IMMEDIATE TRANSACTION");
            try {
                if (get_schema_version() >= v) {
                    // Another process already applied v while we waited.
                    exec("COMMIT");
                    exec("PRAGMA foreign_keys=ON");
                    continue;
                }
                if (v == 6) {
                    // Probe first (SQLite lacks IF NOT EXISTS for ALTER TABLE):
                    // a DB created fresh at a later CURRENT_SCHEMA_VERSION already
                    // has this column via init_schema()'s CREATE TABLE.
                    sqlite3_stmt* stmt;
                    int rc = sqlite3_prepare_v2(db_, "SELECT effective_date FROM images LIMIT 0",
                                                -1, &stmt, nullptr);
                    if (rc != SQLITE_OK) {
                        exec("ALTER TABLE images ADD COLUMN effective_date TEXT");
                    } else {
                        sqlite3_finalize(stmt);
                    }
                }
                if (!migrations()[v].empty()) exec(migrations()[v]);
                set_schema_version(v);
                // Before COMMIT, not after: a violation found afterwards is
                // already durable and there is nothing left to roll back. This
                // catches a migration that stranded child rows. It does not
                // catch one that let the cascade delete them — that leaves no
                // orphans and so no violations.
                int violations = foreign_key_violations();
                if (violations > 0) {
                    throw std::runtime_error("migration to schema v" + std::to_string(v) +
                                             " left " + std::to_string(violations) +
                                             " foreign key violations");
                }
                exec("COMMIT");
            } catch (...) {
                exec("ROLLBACK");
                exec("PRAGMA foreign_keys=ON");
                throw;
            }
            exec("PRAGMA foreign_keys=ON");
        }
```

- [ ] **Step 1: Write the failing test**

Add to `tests/test_database.cpp`. It rewinds to a genuine v8 `images` table by
hand, on the model of `FacesMigrationV8.PreservesIdsLabelsAndVectorsAndStopsReuse`

```cpp
TEST(ImagesMigrationV9, PreservesRowsIdsTagsFavoritesFacesAndLabels) {
    auto dir = make_temp_dir("images-v9");
    auto db_path = (dir / "test.db").string();

    std::vector<int64_t> ids;
    {
        Database db(db_path);
        db.init_schema();

        // Rewind to a v8 images table: plain INTEGER PRIMARY KEY, and the five
        // indexes a v8 database carries. Children are left in place so the
        // migration has real cascade targets to protect.
        const char* rewind = R"(
            PRAGMA foreign_keys=OFF;
            CREATE TABLE images_old (
                id          INTEGER PRIMARY KEY,
                path        TEXT NOT NULL UNIQUE,
                filename    TEXT NOT NULL,
                extension   TEXT NOT NULL,
                file_size   INTEGER NOT NULL,
                created_at  TEXT,
                modified_at TEXT,
                sha256      TEXT NOT NULL,
                phash       INTEGER NOT NULL,
                width       INTEGER,
                height      INTEGER,
                metadata    TEXT,
                media_type  TEXT NOT NULL DEFAULT 'image',
                duration_ms INTEGER,
                gallery     TEXT,
                blur_score  REAL,
                effective_date TEXT
            );
            DROP TABLE images;
            ALTER TABLE images_old RENAME TO images;
            CREATE INDEX IF NOT EXISTS idx_phash ON images(phash);
            CREATE INDEX IF NOT EXISTS idx_sha256 ON images(sha256);
            CREATE INDEX IF NOT EXISTS idx_path ON images(path);
            CREATE INDEX IF NOT EXISTS idx_gallery ON images(gallery);
            CREATE INDEX IF NOT EXISTS idx_effective_date ON images(effective_date DESC, id DESC);
            PRAGMA foreign_keys=ON;
            UPDATE meta SET value = '8' WHERE key = 'schema_version';
        )";
        ASSERT_EQ(sqlite3_exec(db.db_ptr(), rewind, nullptr, nullptr, nullptr), SQLITE_OK)
            << sqlite3_errmsg(db.db_ptr());

        for (int i = 0; i < 3; i++) {
            ImageInfo info;
            info.path = "/p/" + std::to_string(i) + ".jpg";
            info.filename = std::to_string(i) + ".jpg";
            info.extension = "jpg";
            info.file_size = 1000 + i;
            info.sha256 = "sha" + std::to_string(i);
            info.metadata_json = "{\"Make\":\"Canon\"}";
            info.gallery = "trip";
            db.insert(info);
            ids.push_back(db.get_image_id(info.path));
        }
        db.set_tag({"/p/0.jpg"}, "keep", true);
        db.set_tag({"/p/1.jpg"}, "favorite", true);

        // Alice goes on /p/0.jpg, which survives. Putting her on the image
        // deleted below to demonstrate id reuse would cascade her face away
        // before the migration ever ran, and the test would be asserting
        // against a label that was already gone.
        FaceInfo fi;
        fi.embedding.fill(0.25f);
        fi.x = fi.y = fi.width = fi.height = 4;
        int64_t face = db.insert_face(ids[0], fi);
        ASSERT_TRUE(db.set_face_person(face, db.get_or_create_person("Alice")));

        // The rewind is real: on this table a deleted id comes back.
        int64_t top = ids.back();
        db.delete_paths({"/p/2.jpg"});
        ImageInfo again;
        again.path = "/p/again.jpg";
        again.filename = "again.jpg";
        again.extension = "jpg";
        again.file_size = 2000;
        again.sha256 = "sha_again";
        again.metadata_json = "{}";
        db.insert(again);
        ASSERT_EQ(db.get_image_id("/p/again.jpg"), top)
            << "the v8 rewind did not produce a reusing table";
        ids.back() = top;

        // Re-attach a face and a tag to the reused id so the migration has a
        // full set of children to carry across.
        db.set_tag({"/p/again.jpg"}, "keep", true);
        FaceInfo fi2;
        fi2.embedding.fill(0.75f);
        fi2.x = fi2.y = fi2.width = fi2.height = 8;
        db.insert_face(top, fi2);
    }

    // Reopening runs the v9 migration.
    Database db(db_path);
    db.init_schema();
    EXPECT_EQ(db.schema_version(), 9);
    EXPECT_EQ(db.foreign_key_violations(), 0);

    // Every row and every id survived.
    std::vector<int64_t> after;
    sqlite3_stmt* s = nullptr;
    ASSERT_EQ(sqlite3_prepare_v2(db.db_ptr(), "SELECT id FROM images ORDER BY id", -1, &s, nullptr),
              SQLITE_OK);
    while (sqlite3_step(s) == SQLITE_ROW) after.push_back(sqlite3_column_int64(s, 0));
    sqlite3_finalize(s);
    std::sort(ids.begin(), ids.end());
    EXPECT_EQ(after, ids) << "image ids changed, so every tag and face now points elsewhere";

    // The cascade did not fire: tags, favorites, faces and labels are intact.
    EXPECT_EQ(db.get_tags_for_image("/p/0.jpg"), std::vector<std::string>{"keep"});
    auto favs = db.get_tags_for_image("/p/1.jpg");
    EXPECT_NE(std::find(favs.begin(), favs.end(), "favorite"), favs.end())
        << "the favorite tag did not survive the rebuild";
    EXPECT_EQ(db.get_tags_for_image("/p/again.jpg"), std::vector<std::string>{"keep"});

    auto people = db.list_people();
    ASSERT_EQ(people.size(), 1u);
    EXPECT_EQ(people[0].name, "Alice");
    EXPECT_EQ(people[0].face_count, 1) << "the person label did not survive the rebuild";

    // Ordinary columns came across unchanged.
    auto rows = db.get_all_images();
    ASSERT_FALSE(rows.empty());
    for (const auto& r : rows) {
        if (r.path == "/p/0.jpg") {
            EXPECT_EQ(r.sha256, "sha0");
            EXPECT_EQ(r.file_size, 1000);
            EXPECT_EQ(r.gallery, "trip");
            EXPECT_EQ(r.metadata_json, "{\"Make\":\"Canon\"}");
        }
    }

    // And the property the migration exists for now holds.
    int64_t top = ids.back();
    db.delete_paths({"/p/again.jpg"});
    ImageInfo last;
    last.path = "/p/last.jpg";
    last.filename = "last.jpg";
    last.extension = "jpg";
    last.file_size = 3000;
    last.sha256 = "sha_last";
    last.metadata_json = "{}";
    db.insert(last);
    EXPECT_GT(db.get_image_id("/p/last.jpg"), top) << "the migrated table still reuses ids";
}
```
